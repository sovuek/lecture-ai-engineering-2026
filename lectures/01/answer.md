#### 考察

- **temperature 0 でも毎回同じにはならなかった。** 0 は「いちばん確率の高い語を選ぶ」設定だが、出力長が 416〜677 と変わった。API 側の計算の非決定性などで、完全な再現は保証されないらしい。ただし、構成や書き出しはとても似ていた。（出力の長さの幅は、むしろ 2.0 のほうが小さかった：468〜560）
- **temperature 1.0 がいちばんばらついた。** 回答の方針そのもの（「分からない」と断るか、複数の解釈を並べるか）が変わった。同じ質問でも、実行するたびに違う答えが返ることがよくわかった。
- **temperature 2.0 は思ったほど崩れなかった。** 最大値なので意味不明な文になると予想したが、0.0 と同程度に安定していた。Gemini 3 系はモデル側で温度の影響が抑えられている可能性がある。3回だけなので、断定はできない。
- **どの設定でも正解にはならなかった。** temperature はばらつきを変えるだけで、モデルが知らない「講座固有の事実」は出てこない。正しく答えさせるには、第3回でやるように用語集を検索させる（外から情報を渡す）必要がある。
- **flash は lite より約4倍遅く、出力の約2倍の「思考トークン」を使っていた。** 考える分、具体的で説得力のある答えになったが、講座については間違ったままで、むしろもっともらしい作り話が増えた。「賢いモデルほど知らないことを上手に答えてしまう」こともあると感じた。

### 実装：会話履歴を保ったまま続けて質問する

#### やったこと

`app/ask.py` に `--chat` オプションを追加した。

- LLM の API は前の質問を覚えていない（毎回まっさらな状態で答える）。そこで、これまでの質問と回答を `history`（`types.Content` のリスト）にためて、**毎回の呼び出しで履歴を全部まとめて送る**ようにした
- `exit` / `quit` / `終了` / Ctrl+D で終了し、空の入力は無視する
- API エラー（429 など）が出たときは、その質問を履歴から外して、続けて質問できるようにした
- ついでに `--temperature` も指定できるようにした（基礎で使用）
- API を呼ばないテスト `tests/test_ask.py` を追加した（偽のクライアントで、2回目の呼び出しに1回目の質問と回答が含まれることを確認）。`uv run pytest -q` で 14 件すべて成功

#### 結果

```text
$ uv run python -m app.ask --chat
[model] gemini-3.5-flash-lite
あなた> 私の名前はケイです。覚えておいてください。
モデル> ケイさんですね。承知いたしました！しっかりと覚えておきますね。
[トークン数] 入力: 12, 出力: 25
[履歴] 2 メッセージ
あなた> 私の名前は何でしたか？
モデル> ケイさんです！ちゃんと覚えていますよ。
[トークン数] 入力: 45, 出力: 9
[履歴] 4 メッセージ
あなた> さっきの答えを英語で一言で言って
モデル> Kei!
[トークン数] 入力: 67, 出力: 3
[履歴] 6 メッセージ
```

比較のため、履歴なし（従来の1回だけの呼び出し）で同じことを聞くと、覚えていなかった。

```text
$ uv run python -m app.ask "私の名前は何でしたか？"
[トークン数] 入力: 7, 出力: 32
申し訳ありませんが、私たちは始まったばかりの会話ですので、まだあなたの名前を伺っておりません。
```

#### 考察

- 「モデルが覚えている」のではなく、「こちらが毎回、過去の会話を全部送っている」から続けて話せる、ということが実装してわかった。
- そのため、**入力トークン数が 12 → 45 → 67 と、会話が続くほど増えていく。** 長く話すほど1回あたりのトークン数（＝料金や無料枠の消費）と応答時間が増えるので、実際のアプリでは古い履歴を削る・要約するなどの工夫が必要になりそう。

### 発展：応答時間とトークン数の計測と、レート制限

#### やったこと

1. **モデル × 質問の比較（bench）**：3モデル × 性質の違う3つの質問 × 2回 ＝ 18回。`time.perf_counter()` で `generate_content` の前後の時間を測り、`usage_metadata` から入力・出力・思考・合計トークン数を記録した。呼び出しの間は5秒あけた
   - 短い質問：「1+1は？数字だけで答えてください。」
   - 一般的な質問：「LoRAとは何ですか？」
   - 講座に固有の質問：「AIE2026の講座の宿題にある「3レベル」とは何ですか？」
2. **連続呼び出し（burst）**：flash-lite に短い質問を、待ち時間なしで20回続けて送り、何回目でレート制限（429）が出るかを見た

```bash
uv run python -m scripts.lec01_experiment bench
uv run python -m scripts.lec01_experiment burst
```

#### 結果1：モデル × 質問（各2回の平均）

| モデル | 質問 | 応答時間 | 入力 | 出力 | 思考 | 合計 |
|---|---|---|---|---|---|---|
| gemini-3.5-flash-lite | 1+1 | 0.9秒 | 12 | 1 | 0 | 13 |
| gemini-3.5-flash-lite | LoRA | 3.2秒 | 7 | 606 | 0 | 613 |
| gemini-3.5-flash-lite | 3レベル | 3.1秒 | 21 | 556 | 0 | 576 |
| gemini-3.5-flash | 1+1 | 1.5秒 | 12 | 1 | 126 | 140 |
| gemini-3.5-flash | LoRA | 12.4秒 | 7 | 710 | 1093 | 1810 |
| gemini-3.5-flash | 3レベル | 16.1秒 | 21 | 603 | 1062 | 1686 |
| gemini-3.1-flash-lite | 1+1 | 1.1秒 | 12 | 1 | 0 | 13 |
| gemini-3.1-flash-lite | LoRA | 3.3秒 | 7 | 776 | 0 | 784 |
| gemini-3.1-flash-lite | 3レベル | 5.3秒（2.5〜8.1） | 21 | 598 | 0 | 618 |

- 18回すべて成功。gemini-3.5-flash で1回 503（混雑）が出て、30秒待って再試行したら成功した（基礎でも flash で1回 503）
- 429（レート制限）は一度も出なかった

#### 結果2：待たずに20回連続（gemini-3.5-flash-lite）

- **20回すべて成功し、429 は出なかった。** 20回が約25秒で終わった（1分あたりに換算すると約48回のペース）
- 1回の応答時間はふだん 0.6〜1.0秒だが、8〜11回目と13回目、16回目は 1.3〜3.3秒に延びた。その後はまた 0.7秒前後に戻った

#### 考察

- **応答時間は、ほぼ「出力＋思考トークンの量」で決まる。** 入力はどれも 7〜21 トークンと小さく、時間にはほとんど効いていない。同じモデルでも、1トークンで済む「1+1」は約1秒、600トークン前後を書く質問は約3秒だった。lite 系はおよそ 200 トークン/秒で文章を出していた。
- **gemini-3.5-flash は「思考トークン」があるぶん遅い。** 回答には表示されない思考に約1100トークンを使い、合計トークンは lite の約3倍、応答時間は約4〜5倍になった。「1+1」でも 126 トークン考えていた。思考トークンも課金・トークン上限の対象になるので、簡単な質問に flash を使うのはもったいない。講座の既定が lite になっている理由がわかった。
- **3.5-flash-lite と 3.1-flash-lite に大きな差はなかった。** 3.1 のほうが少し長く書く傾向（LoRA で 776 対 606）があった。3.1 の「3レベル」で 8.1 秒かかった回が1回あり、時間は毎回の混み具合でも変わる。
- **レート制限との関係**
  - 公式ドキュメントによると、レート制限は1分あたりのリクエスト数（RPM）・トークン数（TPM）、1日あたりのリクエスト数（RPD）などで決まる。**APIキーごとではなくプロジェクトごと**にかかり、RPD は太平洋時間の0時（今日は日本時間16時）にリセットされる。無料枠の具体的な数値は AI Studio の画面で確認する仕組みになっていて、ドキュメントには載っていなかった。
  - 今回は連続20回（約48回/分ペース）でも 429 は出なかった。少なくとも flash-lite では、今回の使い方で RPM の上限には届かなかった。途中で応答が一時的に遅くなったのは、サーバー側の混雑か、間隔を詰めすぎたことによるものかもしれないが、今回のデータでは区別できない。
  - 今回の実験で、再試行を含めて合計 約56 回 API を呼んだ。1日の上限（RPD）はリクエストの「回数」で数えるので、トークンが少ない「1+1」でも1回は1回として消費される。一方、TPM（トークン数）の制限では、**思考トークンを多く使う flash や、会話履歴を毎回送る `--chat`（実装課題で入力が 12→45→67 と増えた）が先に効いてくる**と考えられる。
  - 実際に困ったのは 429 ではなく **503（モデルの混雑）**で、2回とも gemini-3.5-flash で起きた。無料枠では「上限」だけでなく「混み具合」でも失敗するので、スクリプトには待って再試行する処理が必要だと感じた（`scripts/lec01_experiment.py` では 429/503 のとき30秒待って最大3回再試行している）。
  - 第3回以降のエージェントは1つの質問で LLM を何回も呼ぶので、今回の結果からすると、モデルは lite を使い、呼び出し間隔をあけ、再試行を入れておくのがよさそう。
